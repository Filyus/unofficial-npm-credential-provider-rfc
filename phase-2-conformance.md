# Phase 2 conformance

What the conformance material for [Phase 2](phase-2-credential-provider.md) checks, rule by rule, and what only an npm client can show. The rules are data in [`spec/policy-v1.json`](spec/policy-v1.json); the schema, a Python model of the client, a Rust client and provider pair and the reference providers in [examples](examples/README.md) are held against them.

| Artifact | What it is |
|---|---|
| [spec/protocol-v1.schema.json](spec/protocol-v1.schema.json) | JSON Schema of every message |
| [spec/policy-v1.json](spec/policy-v1.json), [summary](spec/generated-policy-summary.md) | The rules as data: timeouts, cache, fallback, chain, rejection |
| [tests/generated_protocol_vectors.json](tests/generated_protocol_vectors.json) | Valid and invalid messages generated from the policy |
| [tests/](tests) | An executable Python model of the client, with transcripts |
| [poc/rust](poc/rust) | A Rust client and mock provider pair |

Prerequisites and the commands that run all of it are in the [README](README.md#running-the-checks).

## Rule by rule

Each row is a rule of Phase 2 and what backs it, written as `kind: text`: `spec` is a key of the policy; `py` a test module in [`tests/`](tests), or `module.test_name` or `module.Class.test_name` for a test in it; `js` a test title in [`examples/providers/*.test.js`](examples/providers); `rs` a Rust test function under [`poc/rust/crates`](poc/rust/crates). [`poc/claims/check.js`](poc/claims/check.js) confirms in CI that each one still exists. A bare `py` module name proves only that the file exists, and finding a test does not show that it asserts what the row says: that is for the row's wording and for a reader of the test. Evidence given as a link to a file is not looked up.

## Differential fuzzing history

- The nightly of 2026-10-19 (run 39191203253, 4 503 000 messages) found one case in dispute: the request kind `"logi\n"`, which the Python model and the JavaScript providers refused and the schema accepted, because Python's `jsonschema` lets `$` match before a trailing newline. The readers were right, and the schema's pattern was tightened after it.
- Before that run, a run of 100 s covered 756 000 messages with none in dispute (measured once, not re-run by CI).

## What only an npm client can show

npm has no Phase 2 client, and the Rust `mock-client` is a test harness for the protocol, not an npm client. These behaviours are not verified against npm. Where the Python model can show what npm would do, a test pins that; it shows the rule, not that npm follows it:

- masking and control-character stripping of provider stderr and error messages;
- the `.cmd` argument quoting and refusals;
- the Windows working-directory limit for providers;
- `${VAR}` expansion of per-registry provider lists;
- who owns the provider process, and that npm resolves two entries to one identity (resolved path and arguments) before it starts a process: the model says what follows from an identity, not that npm computes it;
- that an interactive request goes through npm's input bracket, and that npm prints its one line naming the provider and the registry, and saying that Ctrl-C stops it, before it hands the terminal over;
- the `warn` and `verbose` logs for providers without `registries`: that a provider in a global chain whose hello has none is logged at `verbose`, and that the stored-token fallback after it declined a registry is a `warn` naming it (`py: test_client_behaviour.LoggingTests.test_a_provider_without_registries_is_logged_at_verbose_and_the_fallback_at_warn`, `py: test_client_behaviour.LoggingTests.test_a_per_registry_list_logs_nothing_at_verbose_about_registries`, `py: test_client_behaviour.LoggingTests.test_a_chain_in_which_every_provider_lists_its_registries_logs_nothing`); the model says what is logged at which level, not that npm writes it at that level;
- the error for a declined URL form on a listed host names the remedy, a per-registry list that holds just `npm:token` (`py: test_client_behaviour.LoggingTests.test_the_error_for_a_declined_form_names_the_remedy`);
- that npm kills a provider with a request outstanding when it exits, after Ctrl-C or a failure elsewhere, and closes the stdin of an idle one (`py: test_client_behaviour.NpmExitTests.test_a_provider_with_a_request_outstanding_is_killed`, `py: test_client_behaviour.NpmExitTests.test_an_idle_provider_gets_its_stdin_closed`); the Rust harness's `Drop` kills a provider that is still running, which is all it shows;
- operation selection: which operation each command sends, that `--dry-run` turns `publish`, `unpublish` and `deprecate` into reads and changes no other command, that `profile enable-2fa` is refused under a provider and `disable-2fa` is not (`py: test_client_behaviour.OperationSelectionTests.test_every_command_sends_the_operation_of_its_row`, `py: test_client_behaviour.OperationSelectionTests.test_the_spec_table_lists_each_command_in_the_row_of_its_operation`, `py: test_client_behaviour.OperationSelectionTests.test_dry_run_turns_publish_unpublish_and_deprecate_into_reads`, `py: test_client_behaviour.OperationSelectionTests.test_every_other_command_sends_its_operation_whatever_dry_run_says`, `py: test_client_behaviour.OperationSelectionTests.test_enable_2fa_is_refused_under_a_provider_and_disable_2fa_is_not`); that npm's commands pass these operations is not shown;
- that the `login` token is never logged at any level (`py: test_client_behaviour.LoggingTests.test_the_login_token_is_never_logged`);
- warning counts: a stored credential used after a global chain declined a registry is warned about once per registry per command, and one that a per-registry list ignores on every command, once in each (`py: test_client_behaviour.WarningCountTests.test_the_fallback_is_said_once_per_registry_per_command`, `py: test_client_behaviour.WarningCountTests.test_a_stored_credential_a_list_ignores_is_said_in_every_command`).
