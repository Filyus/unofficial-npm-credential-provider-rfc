# Phase 2 implementation

What is submitted for [Phase 2](phase-2-credential-provider.md), what the conformance material checks rule by rule, and what only an npm client can show. [Submissions](#submissions) lists the three upstream submissions. [Rule by rule](#rule-by-rule) maps each rule of the protocol to the submission that carries it and to the test behind it. The rules are data in [`spec/policy-v1.json`](spec/policy-v1.json); the schema, a Python model of the client, a Rust client and provider pair and the reference providers in [examples](examples/README.md) are held against them.

Unlike [Phase 1a](phase-1a-implementation.md), this phase has no prototype in npm: the protocol is checked against a model of the client and against example providers.

### 1. npm/rfcs: the credential provider RFC

The text is the proposal document itself, and nothing else is submitted with it.

- **What it contains.** The protocol (configuration, messages, the four request kinds, operations, caching, the security model, the provider's lifecycle), the rationale, the prior art, the migration plan, and the open decisions for the npm maintainers. [Appendix A](phase-2-credential-provider.md#appendix-a-operations-in-detail) is normative.
- **Size.** 1012 lines of Markdown (`phase-2-credential-provider.md`, counted on 2026-10-23).
- **Proposal rules it carries.** All of them: the document is the proposal. The rules are held by the schema, the policy, the generated vectors, the Python model and the Rust pair, which the RFC links as its [conformance material](phase-2-credential-provider.md#implementation).
- **Tests that pin it.** The rows of [Rule by rule](#rule-by-rule) with Submission 1: the schema, the policy and its generated files, the vectors, and the reference providers. The rows with Submission 3 are what the Python model and the Rust client pin of the client's side.
- **How to try it.** `node examples/providers/run.js` runs every reference provider against the transcripts of its example; the commands in the [README](README.md#running-the-checks) run the rest.
- **Before it is opened.** The document links this repository's files (the schema, the vectors, the examples, Phase 1a) relatively; they are made absolute when it is copied to npm/rfcs, which takes one file.

#### Pull request text

```markdown
RFC: a credential provider protocol for npm

## Summary

`credentialProvider` configures a program that npm keeps running for one command and talks to over a small versioned JSON protocol on stdin and stdout, modelled on Cargo's credential providers. npm says which registry, package and npm action it needs a credential for. The provider answers with the credential and how long to cache it, and is told when the registry rejects it. Providers chain, and `npm login` and `npm logout` are delegated along the chain.

## Why

A registry credential in `.npmrc` or in the environment is a standing secret that every install script can read, while registries already issue short-lived, action-scoped credentials. A per-registry token helper, as pnpm has, is the first step and is proposed separately; it cannot say which package or action a token is for, how long it lives, or be told that the registry refused it. This protocol can, so that a provider can hand out a token that reads, one that stages a version and one that publishes.

## What the RFC covers

- Configuration, which only the user's and the global npm config may set.
- The messages: `get`, `erase`, `login`, `logout`, the cache policy and the errors, with a JSON Schema for each.
- Twelve npm actions as operations, so a registry can scope a token to the action.
- The chain, the end of the chain, and what a stored credential does behind it.
- The security model and the threat model.

## Open decisions

Two decisions the maintainers may want to take differently, each of which would make the protocol smaller: shipping the global chain in version 1, and the size of the operation catalogue. The document says what the smaller alternative is for each.

## Conformance material

The schema, the rules as data, generated test vectors, an executable Python model of the client, a Rust client and provider pair, and nine reference providers with transcripts live in the [RFC repository](https://github.com/Filyus/unofficial-npm-credential-provider-rfc/blob/main/phase-2-implementation.md#how-it-is-checked), so npm and third-party providers can be tested against the same cases. The rule-by-rule table, with the test behind each rule, is in the [implementation notes](https://github.com/Filyus/unofficial-npm-credential-provider-rfc/blob/main/phase-2-implementation.md#rule-by-rule).
```

### 2. npm-registry-fetch: a second `getAuthorization` call after a rejection

The library half of the retry; nothing of it is written.

- **What it will contain.** After a 401 or 403, the library calls `opts.getAuthorization` again with `{ regKey, uri, rejected: { status, challenges } }`, and sends the request once more with the value it returns, if any. The [Phase 1a Implementation section](phase-1a-token-helper.md#implementation) describes how Phase 2 uses the seam. The Phase 1a runner returns `undefined` for such a call, so a helper's rejected token is not sent again.
- **Size.** Not yet written.
- **Proposal rules it carries.** The one retry after a rejection and what the retry carries: [`erase`](phase-2-credential-provider.md#erase-a-credential-was-rejected) and the stale-answer rules.
- **Tests that pin it.** None in the library yet. The Python model and the Rust client pin the retry as rows of [Rule by rule](#rule-by-rule) with Submission 2.
- **How to try it.** Not yet possible.

### 3. npm/cli: provider sessions, the chain and the cache

The client half; nothing of it is written.

- **What it will contain.** `@npmcli/config` gains the `credentialProvider` keys, filtered as the trust rule requires. A session object per provider, owned by npm/cli, which spawns the process on first use and ends it with the command. The chain, the cache, the operation each command sends, and `login` and `logout` delegated along the chain. The [Implementation section](phase-2-credential-provider.md#implementation) of the RFC describes one way to do it.
- **Size.** Not yet written.
- **Proposal rules it carries.** Sessions, chaining, caching and operations: [Detailed Explanation](phase-2-credential-provider.md#detailed-explanation), sections 1 to 7.
- **Tests that pin it.** None in npm yet. The rows of [Rule by rule](#rule-by-rule) with Submission 3 are pinned in the Python model and the Rust client, which show the rule and not that npm follows it ([Limits](#limits)).
- **How to try it.** Not yet possible; the reference providers can be run against the Python model and the Rust client.

## Rule by rule

Each row is a rule of Phase 2 and what backs it. The Submission column holds the number of the submission in the [table above](#submissions) that carries it: 1 where the rule is the protocol text itself and is held by the schema, the policy and the reference providers, 2 for the call after a rejection, 3 for what an npm client does; two numbers where a rule is split between them.

The evidence is written as `kind: text`: `spec` is a key of the policy; `py` a test module in [`tests/`](tests), or `module.test_name` or `module.Class.test_name` for a test in it; `js` a test title in [`examples/providers/*.test.js`](examples/providers); `rs` a Rust test function under [`poc/rust/crates`](poc/rust/crates). [`poc/claims/check.js`](poc/claims/check.js) confirms in CI that each one still exists. A bare `py` module name proves only that the file exists, and finding a test does not show that it asserts what the row says: that is for the row's wording and for a reader of the test. Evidence given as a link to a file is not looked up.

### The npmjs.com stage token test

A live test for the one question the RFC leaves to evidence: which token tiers npmjs.com accepts on the staged-publishing reads. The answer is the evidence for a provider's default `stage-read` mapping on npmjs.com, within the scope tested below (npm 11.19.0, one account, one package, HTTP GETs) ([Operations](phase-2-credential-provider.md#4-operations)); it changes nothing in the protocol. The documentation names no tier: the API lists granular tokens on every `/-/stage` path and documents 401 as the only refusal on the list, and 401 and 404 on the record and the tarball ([API](https://api-docs.npmjs.com/)).

It needs an npmjs.com account and real tokens, so it is run by hand.

#### Setup

- An npmjs.com account with 2FA.
- A package P the account already maintains, preferably a throwaway scoped one, so no public placeholder is created; and a second maintained package Q.
- Note P's publishing-access setting. If possible, run T2 and T3 twice: with "Require 2FA" alone and with "Require 2FA and disallow tokens", staging S (below) before switching to the second, since a token presumably cannot stage under it.

#### Tokens

Bypass-2FA off unless stated:

| Token | Kind |
|---|---|
| T1 | Session token from `npm login` (web flow) |
| T2 | Granular, packages read-only, selected to P |
| T3 | Granular, read and write (stage only), P |
| T4 | Granular, read and write (publish and stage), P |
| T5 | Granular, read-only, selected to Q only |
| T6 | Granular with no package access, if the site allows one; otherwise note that it does not |
| T3b | Optional: T3 with bypass-2FA on |

#### Stage one version

In P, run `npm stage publish` with T3 through a throwaway userconfig, which gives a stage id S. Note whether it asks for a one-time password. Confirm S with `npm stage list` under T4. The staged version need not be a real build: `node poc/stage-tiers/run.js pack <dir> <P> 0.0.0-tokentest.1` writes a package whose README says not to approve it, under the dist-tag `tokentest`. If P's publishing access disallows tokens, T3 cannot stage; stage under T1 and note it.

#### Requests

Keep each token out of argv and shell history: put `Authorization: Bearer <token>` in a file `hdr.txt` written with an editor (or under `umask 077`), never with `echo` and the token on the command line, then run `curl -sS -D- -H @hdr.txt <url>`.

| Request | URL |
|---|---|
| R1 | `https://registry.npmjs.org/-/stage?page=0&perPage=100` |
| R2 | R1 plus `&package=<P, URL-encoded>` |
| R3 | `https://registry.npmjs.org/-/stage/S` |
| R4 | `https://registry.npmjs.org/-/stage/S/tarball` (with `-o /dev/null`) |

For each token and request, record the status, the item count or error body, and every `WWW-Authenticate` header. Control: R1–R4 with no `Authorization`, expected 401.

`node poc/stage-tiers/run.js check <token-dir> S <P>` does all of this: it reads each token from its own file (`T2.txt`, or the `T1.npmrc` that `npm login --userconfig` writes), sends it only to registry.npmjs.org, follows no redirect, redacts it from every body, and writes the table to `results.json` in that directory.

#### Reading the results

- **T3 and T4** should give 200 with S on R1–R4. If T3 fails where T4 passes, a stage-only token cannot read its own staged versions. The RFC never answers `stage-read` with a credential that can publish directly, so provider users on npmjs.com then cannot run `stage list`, `view`, `download`, `approve` or `reject`: record that as a gap to report to npm, not as a default.
- **T2** decides it:
  - 200 with S on R1–R4: providers map `stage-read` to a separate read-only token, with no presence check, and it works in CI.
  - 401 or 403: write-capable tokens only, and the RFC's write-policy rule applies. Note which of the two arrives; a 403 is what a provider may widen on.
  - 200 with an empty list, and 404 on R3 and R4: the visibility filter works by tier; same conclusion, and it confirms the RFC's "a 401, a 404 or an empty list".
- **A 401 with `WWW-Authenticate: otp`** on any read is a one-time-password challenge, not a tier refusal ([erase table](phase-2-credential-provider.md#erase-a-credential-was-rejected)), and changes how the T2 row reads.
- **T1:** 200 means session tokens work despite the API's security list; 401 means providers need a granular token.
- **T5:** provided Q has no staged versions, expected an empty list and 404, confirming that a token selected to other packages fails as 404 or an empty list, not 403.
- **T6:** record the outcome. **T3b** against T3: expected the same.

#### Result, 2026-10-17

Run once, by hand, with `poc/stage-tiers/run.js` (so not re-run by CI, and not repeatable without the account, the package and the tokens) with npm 11.19.0 against a scoped package the account maintains, whose versions are published by trusted publishing, with T1–T5 (T6 and T3b skipped, and the publishing-access setting left as it was). T3 staged `0.0.0-tokentest.1` without asking for a one-time password.

| Token | R1 list | R2 list, `package=` | R3 record | R4 tarball |
|---|---|---|---|---|
| none | 401 | 401 | 401 | 401 |
| T1 session | 200, S listed | 200, S listed | 200 | 200 |
| T2 read-only, P | 200, S listed | 200, S listed | 200 | 200 |
| T3 stage only, P | 200, S listed | 200, S listed | 200 | 200 |
| T4 publish and stage, P | 200, S listed | 200, S listed | 200 | 200 |
| T5 read-only, Q only | 200, S listed | 200, S listed | 404 | 404 |

No response carried `WWW-Authenticate`, and none was a one-time-password challenge.

- **T1 to T4, the read-only T2 included, were answered 200 on the list, the record and the tarball; T5, selected only to Q, was answered 200 on both lists and 404 on the record and the tarball** (plain HTTP GETs R1–R4 sent from Node's `fetch` with each token; npm 11.19.0; one account, one package, one staged version; the stricter publishing-access setting was not tried). So, for these requests and no others, a provider could answer `stage-read` on npmjs.com with a separate read-only token and no presence check. The `npm stage list`, `view` and `download` commands were not run with T2–T5, so that they work in CI is not shown by this test.
- **The list is filtered by the account, not by the token:** T5, selected only to Q, still listed P's staged version, while the record and the tarball honoured its selection with 404.
- **The dist-tag in `publishConfig` was not used:** `npm stage publish` reported staging "with tag latest" although `publishConfig.tag` named another tag. The version was rejected, never approved, so what approval would have done to `latest` was not observed.

Afterwards the version was rejected under T1, which npm confirmed through the browser (its web one-time-password flow); `npm stage list` then showed no staged versions, T1 was logged out and T2–T5 revoked.

#### Cleanup

`npm stage reject S` under T1 or T4 with a one-time password (do not approve it); revoke T2–T6 and T3b; `npm logout` for T1; delete `hdr.txt` and the throwaway userconfig.
