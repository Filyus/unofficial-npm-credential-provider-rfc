### 1. npm-registry-fetch: `opts.getAuthorization`

The library gains one option and no process code.

- **What it contains.** `lib/auth.js` walks the registry keys of a request as it does for a stored credential (the URL's keys from the longest up, then the registry's keys for a URL on its host) and asks the function for each. It stops at the first key that holds a stored credential which sets `Authorization`: a token, `_auth`, or a username and password. A certificate and key alone do not stop it. `regFetch()` waits for the function while watching the request body, skips it for `--offline` and `forceAuth`, and sends the value it returns as the `Authorization` header. `getAuth.supportsGetAuthorization` is `true`.
- **Size.** 100 lines added and 13 deleted in `lib/` (`git diff --numstat 6b4159a 2e27571 -- lib`, counted on 2026-10-23), 32 of README and 159 of tests in `test/auth.js`.
- **Proposal rules it carries.** The seam and "no process code in the library" in the proposal's [Implementation](phase-1a-token-helper.md#implementation), and the key walk of [Which requests get the credential](phase-1a-token-helper.md#which-requests-get-the-credential). Nothing about how a credential travels: that is [Phase 1b](phase-1b-credential-hardening.md)'s.
- **Tests that pin it.** The `fetch` rows of [Rule by rule](#rule-by-rule) are titles in `test/auth.js`. tap fails `npm test` below 100% coverage.
- **How to try it.** The first block of [Reproducing the checks](#reproducing-the-checks) applies the patch to the base commit and runs `npm test` and `npm run eslint`. A caller passes `getAuthorization: async ({ regKey, uri }) => 'Bearer ' + token` in the options of any request.

#### Pull request text

```markdown
feat: add opts.getAuthorization, a callback that supplies the Authorization header

## What

`opts.getAuthorization` is an async function a caller can pass. It is given `{ regKey, uri }` and returns the value of the `Authorization` header, or nothing. The library asks it for the keys a stored credential for the request would be looked up under, longest first: the keys of the request's URL, then, for a URL on the registry's own host (a tarball), the keys of the registry. The first value returned is sent.

## Why

Callers that want a credential from a program the user runs, at the moment it is needed, have no way to give it to the library except by writing it into the options first. pnpm has such a setting, `tokenHelper`, and npm users ask for it. A callback lets the caller do that in its own code. The library runs no program and reads no new config key, so a tool that passes it a project's `.npmrc` keys is not made to run anything.

## How it behaves

- The walk ends at the first key that holds a stored credential which sets `Authorization` (a token, `_auth`, a username and password). The function therefore wins over a stored credential for the same key, and a credential stored under a longer key wins over the function's for a shorter one. A key that holds only a client certificate and key sets no `Authorization` and does not stop the walk.
- The value is sent as a stored credential is: same transport options, same `http:` behaviour, same redirects, and the one-time-password retry asks again.
- It is not asked for an `offline` request, or when `forceAuth` is given.
- An error thrown by the function rejects the request unchanged. A body that is a promise or a stream and fails while the function runs rejects the request as well, and a stream is piped into gzip only once the function is done.
- `getAuth.supportsGetAuthorization` is `true`, so a caller that cannot do without the option can tell a library that ignores it.

## What it does not do

It changes nothing for a caller that does not pass the option, and nothing about how any credential is sent once it is chosen.

## Tests and size

159 lines of tests in `test/auth.js`: the arguments, the key order, mTLS at a longer key, a tarball on the registry host and on another host, the value as returned, an error, a failing body, and offline and `forceAuth`. 100 lines added in `lib/`, 32 in the README.

## Context

This is the library half of a proposal for a token helper in npm, written up in [Phase 1a](https://github.com/Filyus/unofficial-npm-credential-provider-rfc/blob/main/phase-1a-token-helper.md#implementation). The rule table and the tests behind it are in the [implementation notes](https://github.com/Filyus/unofficial-npm-credential-provider-rfc/blob/main/phase-1a-implementation.md#1-npm-registry-fetch-optsgetauthorization). I wrote it and will follow up on issues about it.
```

### 2. npm/cli: the token helper

The core of the helper, in `lib/` and `@npmcli/config`.

- **What it contains.** The runner `lib/utils/token-helper.js`, on `@npmcli/promise-spawn`.
  - Config trust: the key is read from user and global files only, not when project config chose them, and not when the command line or the environment chose the file and a directory from its own up holds a `package.json` or a `.git`, the walk ending at home.
  - The route checks, one per request: plain `http:` except to this machine; `ca`, `cafile` and `strict-ssl=false` from the project layer, and `proxy` and `https-proxy` from it for an `http:` request only; a credential for this run.
  - The project layer is the project `.npmrc`, a user or global file the location rule did not trust, the `publishConfig` route values that `publish` and `unpublish` register, and a route value in the environment for a key that a parent npm listed as taken from its project (`npm_config_token_helper_project_transport`, which is how a child npm in any directory sees what its parent took from the project).
  - A second list, `npm_config_token_helper_untrusted`, names the user and global files the parent did not trust that hold a `tokenHelper` key; a child distrusts them whatever path its environment gives. A nested npm in a git dependency's clone has no project `.npmrc` that names the file and no mark above it to tell it. The two lists are independent and both are live.
  - The `getAuthorization` function that `lib/npm.js` builds from the `//<registry>/:tokenHelper` key, with the dependency floor `^20.1.0`. `publishConfig` filtering, `whoami` and `get-identity`, `login`, `logout`, and the docs.
- **Size.** 936 lines added and 7 deleted in `lib/` and `workspaces/config/lib/` (`git diff --numstat ae98c62 3a84c65 -- lib workspaces/config/lib`, counted on 2026-10-24), 426 of them the runner, 369 the config, 22 its export for a child and 2 the update check that asks no helper. Also 82 lines of docs and 2333 of tests and fixtures.
- **Proposal rules it carries.** [Trust](phase-1a-token-helper.md#trust), [Where it may be set](phase-1a-token-helper.md#where-it-may-be-set), [How the helper runs](phase-1a-token-helper.md#how-the-helper-runs), [Output and failures](phase-1a-token-helper.md#output-and-failures), [Which requests get the credential](phase-1a-token-helper.md#which-requests-get-the-credential) and [Precedence and commands](phase-1a-token-helper.md#precedence-and-commands), apart from what submission 3 adds.
- **Tests that pin it.** The `config` and `cli` rows of [Rule by rule](#rule-by-rule) are titles in `workspaces/config/test/` and `test/lib/`, and the `e2e` and `probe` rows are checks in `poc/npm-e2e/run.js` and `poc/platform-probes/run.js`. The runner's tests replace `@npmcli/promise-spawn` with a fake process.
- **How to try it.** [Reproducing the checks](#reproducing-the-checks) builds both trees and runs the end-to-end script against a local registry. By hand: put `//localhost:<port>/:tokenHelper=<absolute path of a script that prints a token>` in `~/.npmrc` and run `npm whoami --registry http://localhost:<port>/` with the prototype's npm-registry-fetch under npm.

#### Pull request text

```markdown
feat: add tokenHelper, a program that prints a registry token

**Draft.** This waits for a release of npm-registry-fetch with `opts.getAuthorization` (20.1.0) and raises the dependency floor to `^20.1.0`. When that release exists the only change here is the dependency bump.

## What

`//<registry>/:tokenHelper=<absolute path>` in the user's or the global npmrc names a program that prints the credential for a registry. It is the setting of the same name that pnpm has, and answers the request for a token helper in npm. npm runs the program when it first needs the credential for that registry and sends the output as the `Authorization` header: a raw token as `Bearer <token>`, output that starts with an auth scheme and a space as it is. A `~/.npmrc` written for pnpm then gives npm the same credential.

## Why

Registries that issue short-lived tokens leave npm with a file that goes stale, and every install script can read a token in `.npmrc`. A helper keeps the credential out of the file and fetches a fresh one when it is needed.

## How it behaves

- The runner (`lib/utils/token-helper.js`) takes one absolute path with no arguments and refuses anything else, and never prints a value that is not an existing file. A `.cmd` or `.bat` file runs through `cmd.exe` on Windows.
- It starts in its own directory with stdin closed, and has 60 seconds and 1 MiB per stream. Its environment lacks the `npm_config_*` variables, `NODE_OPTIONS` as npm set it from a project, and the directories npm put in front of `PATH` for a script.
- It runs once per registry and helper per process, and not for the weekly check for a newer npm. A failure is `ETOKENHELPER`, names the helper's status and never its output, and no other credential is tried.
- A helper wins over a token stored in a file for the same registry, with one warning. A token, `_auth` or username and password given on the command line or in the environment, and an OIDC token, win over the helper.
- `publish`, `whoami` and `get-identity` count a helper as a login. `login` refuses, `logout` explains.

## What is refused, and why

- A helper is a program npm runs, so only the user may name it. In a project or workspace `.npmrc`, `publishConfig`, the environment and on the command line the key is ignored with a warning.
- A user or global file does not count when project config chose it (`userconfig` for the user file, `globalconfig` or `prefix` for the global file), or when the command line or the environment chose it and a directory from the file's real path up holds a `package.json` or a `.git`. The walk stops at home. A child npm applies the same rule, and its parent tells it which files it did not trust, since the child may run in another project and see only an environment value for the file.
- The credential is not sent over plain `http:` except to this machine, and not while `ca` or `cafile` has its value from the project layer (or `strict-ssl` is `false` there), nor `proxy` or `https-proxy` for an `http:` request: over `https:` a proxy sees only a CONNECT tunnel. The project layer is the project `.npmrc`, a user or global file that was chosen inside a project, the `publishConfig` of a `publish` or `unpublish`, and an environment value for a key that a parent npm named as taken from its project. The helper is not run, and the message names the key and the file.
- A fresh helper token is often broader than a stored one, which is why these two routes are stricter for a helper. How any credential travels after it is sent is left alone.

## How it was tested

Unit tests in `workspaces/config` and `test/lib` (tap holds 100% on `@npmcli/config`), an end-to-end run of a real npm against a local registry with each refusal beside a control, output and route fuzzing against a model of the rules, platform probes on Linux, macOS and Windows, and every npm/cli suite with and without the change.

## Size

917 lines added and 7 deleted in `lib/` and `workspaces/config/lib/`, 426 of them the runner and 350 the config trust rules, and 82 lines of docs.
```

### 3. npm/cli: the `profile` guard, the 401 hint and the runner's diagnostics

A follow-up that changes messages only.

- **What it contains.** Three groups of messages.
  - `profile enable-2fa` says why it cannot work through a helper, before it makes a request (which would start the helper), and names neither the helper nor its value.
  - A 401 from a registry that has a helper says that the registry refused the token the helper printed and to refresh the login or the cache of the tool behind it, instead of suggesting `npm login` (`lib/utils/error-message.js`).
  - The runner says more about why a helper could not run: a missing `#!` interpreter is named (and a carriage return at the end of the line as the likely cause), status 127 or 9009 says a tool the script calls was not found, and a `.ps1` or `.js` file on Windows is refused with a pointer to a `.cmd` wrapper.
- **Size.** 88 lines added and 3 deleted in `lib/` (`git diff --numstat 3a84c65 315664b -- lib`, counted on 2026-10-24), 4 of docs and 133 of tests.
- **Proposal rules it carries.** The messages of [Output and failures](phase-1a-token-helper.md#output-and-failures), and the 401 and `profile enable-2fa` rows of [Precedence and commands](phase-1a-token-helper.md#precedence-and-commands).
- **Tests that pin it.** `test/lib/commands/profile.js`, `test/lib/utils/error-message.js` and `test/lib/utils/token-helper.js`; the rows of [Rule by rule](#rule-by-rule) with Submission 3.
- **How to try it.** As for submission 2, applied with the second commit of `poc/patches/npm-cli.patch`; run `npm profile enable-2fa` with a helper configured.

## Rule by rule

Each statement of Phase 1a about the prototype is pinned to a test or a check, written as `kind: text`. The Submission column holds the number of the submission in the [table above](#submissions) whose code makes the rule true, and two numbers where the rule is split between them. [`poc/claims/check.js`](poc/claims/check.js) confirms in CI that each one still exists, so a renamed or deleted test fails instead of leaving a claim without evidence.

What the check proves: it finds the text as a substring of the files of its kind. It does not run the test, and finding the text does not show that the test asserts what the row says: that is for the row's wording and for a reader of the test.

Kinds: `fetch` is a test title in npm-registry-fetch `test/auth.js`; `config` a test title in npm-cli `workspaces/config/test/`; `cli` a test title in npm-cli `test/lib/`; `e2e` a scenario or a check in [`poc/npm-e2e/run.js`](poc/npm-e2e/run.js); `probe` a check (not an `info` line) in [`poc/platform-probes/run.js`](poc/platform-probes/run.js); `py` a test in [`tests/`](tests), as `module.test_name` or `module.Class.test_name`; `spec` a key of [`spec/policy-v1.json`](spec/policy-v1.json).

## Limits

Each row is one of two things, and the kind is in the first column. A **limit** is outside what the Phase 1a checks claim, for the reason given, and says what would make the claim wider. **Deferred** work is something that can be done and is not, with the number of the task in the project's tracker that follows it. A third kind, a defect, is not listed: it is fixed, and the closed ones are named under the table.

How a credential travels after it is sent (redirects, the HTTP cache index, error responses) is [Phase 1b](phase-1b-credential-hardening.md)'s. For 1a the claim about a helper's credential is the refusals in [Which requests get the credential](#which-requests-get-the-credential), and that after them it does what a stored token's does.

| Kind | Not claimed | Why | Wider if |

### Retired mechanisms

Eight mechanisms of the prototype were replaced or dropped and are retired, four by the fourth round, four by [pass 1](#pass-1) and one by [pass 2](#pass-2). A ninth, the marker of the untrusted files, was retired in pass 1 and has been live again since [pass 3](#pass-3).

None is deleted: [`poc/retired`](poc/retired) holds a patch for each that applies on top of the prototype and restores the mechanism with its tests, and the [`retired` workflow](.github/workflows/retired.yml) applies each one weekly and on every change, runs the tests it restores and fails if one does not apply or pass. The [README there](poc/retired/README.md) says what each protected, why it went and what would bring it back; the decision in the project's knowledge base is 121 for the first four and 122 (with observation 777) for pass 1; passes 2 and 3 work from the same matrix (observation 777).

- `child-env-equals-project`: counting a route value in a child's environment as the project's when the current project's `.npmrc` holds the same value (pass 2, R28: a nested npm in another project escaped it; the marker of the fourth round, which had been replaced by it, is live again).
- `helper-env-editor-node-env-color`: taking `EDITOR`, `NODE_ENV` and `COLOR` out of the helper's environment.
- `route-proxy-over-https`: refusing a project's `proxy` and `https-proxy` for an `https:` request.
- `publish-config-precheck`: refusing a `publishConfig` route key before the request, in `publish` and `unpublish`.
- `cmd-path-characters`: refusing a `.cmd` or `.bat` helper path that contains `"`, `%` or `!` (pass 1: the path is the user's own).
- `stderr-control-characters`: removing control characters from the helper's stderr lines; the masking of the exact token stays (pass 1: only the helper writes them).
- `config-set-refusals`: `npm config set` refusing `tokenHelper` in project config and the unscoped form (pass 1: the warnings at load time already say both).
- `helper-exit-code-field`: the `helperExitCode` property of `ETOKENHELPER`; the message names the status and `signal` stays (pass 1: nothing reads the field).

Each patch is applied alone, as `run.js` does. The patches were regenerated against the prototype where the fixes moved their context: after pass 1, `publish-config-precheck` (the tests of the `publishConfig` route no longer depend on which npm-registry-fetch is installed); after pass 2, `publish-config-precheck` and `route-proxy-over-https` (the documentation line they change moved), and `child-env-equals-project` is new; after pass 3, `child-env-equals-project` and `publish-config-precheck` (the documentation paragraph about a child npm grew), and `child-untrusted-marker` left the folder, since it is part of the prototype.

After pass 7, `publish-config-precheck` was regenerated again: the new test of `unpublish` (the route of one manifest does not stay for the next) asserts a refusal at the request, and the restored check refuses before it, so the patch changes that test. [`poc/claims/check.js`](poc/claims/check.js) fails when a patch in the folder has no row in the README and no entry in `retired.json`, or the other way round.

After pass 8, `child-env-equals-project` was regenerated: the lines it changes in `tokenHelperProjectTransport` moved when the route rule learned that a project file may be the user's own.

## How it is checked

### Coverage

tap's check fails `npm test` below 100%, and CI runs it wherever `npm test` runs.

- npm-registry-fetch and `@npmcli/config`: on every run.
- The rest of npm/cli: only inside the `full-suites` job, which runs each suite's `npm test` with and without the prototype and counts a suite that fails with no failing test file as a regression, but only where the base passes. A coverage shortfall in a suite that already fails on the base is not caught.
- The workflow's targeted step for the npm/cli files the prototype changes runs with `--no-coverage` and checks no coverage; the runner's own file has 100% in a local run of its test.

What the end-to-end run checks:

- Helpers in user config work. Project, `publishConfig` and child-process routes are refused. A helper beats a stored `_authToken` with one warning; a credential on the command line, in the environment or an OIDC token beats a helper.
- A file chosen on the command line or in the environment is refused inside a repository (a `.git` alone, a worktree's `.git` file, `location=global`, a directory below home, a dotfiles repository) and honoured outside one.
- Plain `http:` to another host, a project's CA or `strict-ssl=false`, a project's proxy for an `http:` request, a CA in a user file the environment chose inside the checkout, and a `publishConfig` CA or proxy are refused with the helper not run. Loopback, a project's proxy for an `https:` request, and the same settings from the command line, the environment or a user file outside the checkout, are not. A child npm, in the repository or in another project, refuses what its parent took from the project and not a value the user set.
- A failing helper is npm's error with npm's own exit status, and a helper that runs npm starts no helper in it.
- `NODE_OPTIONS` from a project reaches no helper, also one npm further down, and does reach it where it is the user's own. `NODE_ENV` and `COLOR` reach it as npm has them. Redirects and a foreign tarball treat the credential as a stored token's.

The [CI workflow](.github/workflows/prototype.yml) runs all of it on macOS, Linux and Windows, with Node 22.22.2, 24.15.0 and 26.x, except the comparison of every npm/cli suite with and without the prototype, which runs on Ubuntu and Windows with Node 24; on 26.x the prototype's own code runs with deprecations as errors.

Retired with the split, and kept on `phase-1-hardened`: the 2048-combination config matrix, the trust fuzzer and the spelling fuzzer, the probes for containment by device and inode (letter case, Unicode forms, linked temp directories, FAT32 volumes), and the end-to-end checks for redirect hops, error responses and the cache. Phase 1a's location rule looks for a mark in each directory from the file's real path up and compares no identities, so the spellings those probes tried (case, Unicode forms, `\..\`) have no effect on it: a mark is looked up by path, which every spelling serves. The 1b checks return with 1b.

A test that cannot make a link (a file outside the project that links to one inside it) skips itself, and tap counts a skip as a pass. The workflow therefore fails on Linux and macOS, where links can be made, if tap reports any skip in the config tests.

What the macOS runs showed about the platform: a helper script without a `#!` line fails with ENOEXEC there, while Linux runs it through `/bin/sh`. The probes assert it (macOS, and Linux for the second half). The earlier probes' findings about case, Unicode forms and `/var` links were evidence for identity; what the lexical rule relies on is [recorded in sources.md](sources.md#external-facts) and is on the hardened branch.

### Reproducing the checks

The `token-helper` branches are not published; the prototype is the two patches in [poc/patches](poc/patches), made against fixed upstream commits. These are the steps of the [CI workflow](.github/workflows/prototype.yml) (`NPM_CLI_BASE`, `NPM_REGISTRY_FETCH_BASE` and the `prototype` job), in a POSIX shell, starting in an empty working directory that holds a checkout of this repository as `rfc`. The Windows runs also set `core.longpaths` (npm/cli has fixtures deeper than its path limit) and `core.autocrlf false` (the patches have LF endings). Use Node 22.22.2, 24.15.0 or 26.x, and Python 3.12 with `jsonschema` for the Python step.

```sh
git config --global core.autocrlf false
git config --global core.longpaths true      # Windows only
NPM_CLI_BASE=ae98c62586b6fea44114f72e249e246a2981de70
NPM_REGISTRY_FETCH_BASE=6b4159a2519ce5aab26cc4dd8d4596a0b47781d2

# npm-registry-fetch at its base commit, with the patch applied
git init -q npm-registry-fetch
(cd npm-registry-fetch &&
  git fetch -q --depth 1 https://github.com/npm/npm-registry-fetch.git "$NPM_REGISTRY_FETCH_BASE" &&
  git checkout -q FETCH_HEAD &&
  git -c user.name=ci -c user.email=ci@localhost am -q ../rfc/poc/patches/npm-registry-fetch.patch &&
  npm install --ignore-scripts --no-audit --no-fund &&
  npm test --ignore-scripts && npm run eslint --ignore-scripts)

# npm/cli at its base commit, dependencies installed, then the two commits of
# the patch (it raises the npm-registry-fetch floor to ^20.1.0, which is not
# published, so the install comes first)
git init -q npm-cli
(cd npm-cli &&
  git fetch -q --depth 1 https://github.com/npm/cli.git "$NPM_CLI_BASE" &&
  git checkout -q FETCH_HEAD &&
  node scripts/resetdeps.js &&
  git -c user.name=ci -c user.email=ci@localhost am -q ../rfc/poc/patches/npm-cli.patch &&
  node . test --ignore-scripts --workspace @npmcli/config)

# the checks that need the trees (the end-to-end run overlays the prototype's
# npm-registry-fetch on npm/cli's bundled copy and undoes it before it exits)
node rfc/poc/npm-e2e/run.js npm-cli npm-registry-fetch
node rfc/poc/platform-probes/run.js npm-cli
node rfc/poc/helper-fuzz/names.js npm-cli
(cd rfc && python3 -m tests.fuzz_helper --prototype ../npm-cli --seconds 20 --seed 1)
node rfc/poc/claims/check.js npm-cli npm-registry-fetch
```

The workflow also runs the npm/cli files the prototype changes with `node node_modules/tap/bin/run.js --no-coverage` (the step "Test the npm-cli files the prototype changes"), and its `full-suites` job builds a base tree and a patched tree and compares every suite (`node rfc/poc/full-suites/compare.js base next`; the job allows 150 minutes, and its tree setup is in the workflow). With `NPM_CLI=<npm-cli checkout>` set, `python -m unittest discover` also runs the helper comparison of [`tests/test_helper_differential.py`](tests/test_helper_differential.py).

[`poc/full-suites/compare.js`](poc/full-suites/compare.js) is run by CI and counts a test file as a regression only when it fails all three reruns with the prototype and passes all three without it. A file that fails one or two of the three is listed under "failed once, not every time" and the run still passes: a regression that shows up only intermittently is not caught by the gate, so the list has to be read.

#### The third round

- **Trust.** The roots of the location rule came from the current directory and `localPrefix`, so a repository root with a `.git` and no `package.json`, a nested package, `location=global` in the project and a current directory in no project were missed, and a user's own XDG or `~/.npmrc.work` file was refused when home or the current directory was a root. Fixed: the rule looks at the file's own directories for a `package.json` or a `.git`, stops unchecked at home, and uses no current directory.
- **Split and adoption.** The documents said a helper adds no exposure and behaves like `_authToken`, though it mints a fresh, broad token and fails before the cache. Fixed: plain `http:` and a project's proxy or CA are refused for a helper, and `publishConfig` route keys too; the Summary states the differences and the open decisions name where the maintainers may differ.
- **Protocol.** A credential given for the run lost to the helper, and OIDC had a mask of its own. Fixed: such a credential wins, and OIDC by the same rule.
- **Evidence.** Absences with no control, stale shas and counts, a skipped link test that passed, and documents the workflow did not watch. Fixed: each absence is set beside a control, the numbers are redone, and a skip fails on Linux and macOS.
- **Path identity.** Aliases that a real path does not merge. Stated as a limit, with what would widen it.

#### The fourth round

- **Councils.** One council took the attacker who already runs as the user, CI, and an audit of what the documents claim; the other walked scenarios: a developer machine, CI, registries and a hostile repository.
- **The claims.** The documents said a helper protects against what only a repository's config can do. Fixed: [What this protects against, and what it does not](phase-1a-token-helper.md#what-this-protects-against-and-what-it-does-not) says it holds for commands that run no repository code, helps against leaks and scrapers of npm's own files, and does not hold against code already running as the user or in the job, which can run the helper or read the vendor's store or a keychain. The trust rule and the location rule are repository isolation. The proposal also answers why `git=` and `script-shell` may come from a project and `tokenHelper` may not, and qualifies the Shai-Hulud motivation.
- **The route.** A project `proxy` or `https-proxy` refused `https:` requests too, which broke corporate repositories and protected nothing, since a proxy sees only a tunnel (`route-proxy-over-https`, retired); it refuses an `http:` request only. A user or global file the command line or the environment chose inside a project, GitLab's `NPM_CONFIG_USERCONFIG=$CI_PROJECT_DIR/.npmrc`, was the user's for the route keys; it is the project layer. `publishConfig` route values were checked once, before the request, and missed the OIDC order; they are registered and seen by the per-request check (`publish-config-precheck`, retired).
- **Children.** Two markers in the environment kept a child npm in line. A child reads the project `.npmrc` itself, so the first was redundant (`child-untrusted-marker`, restored in pass 3: that holds for `npm run`, not for a nested npm in another project); the second was replaced by a comparison, a route key whose value comes from the environment is the project's when the project `.npmrc` holds the same value (`child-env-equals-project`, retired in pass 2: the comparison missed a child in another project, and the marker is back). The case left then was a script that leaves the project; the marker of pass 3 closes it for npm parents.
- **The environment.** `EDITOR`, `NODE_ENV` and `COLOR` were taken out of the helper's environment and recognised by looking at what a parent had exported, which lost the user's own values and protected nothing: none carries code or a credential into a helper (`helper-env-editor-node-env-color`, retired).
- **The vendors.** `gh auth token` is no longer the GitHub migration (its token carries `repo`, `read:org` and `gist`); the AWS command carries `--duration-seconds 900`; the Google Artifact Registry row follows Google's own tool and prints a Bearer token; the pnpm claim is narrowed to a Bearer token, an `https:` registry and a path without spaces, `$`, `%` or quotes.
- **Evidence.** The end-to-end run gained a control for every new refusal, and each retired mechanism is checked by CI to be restorable.

- **Fixed.** A file that is there and is not a regular file, or cannot be resolved, is refused with a message; a file that is not there still has no key to refuse, and `/dev/null`, which people give to switch the user file off, holds no line to refuse.
- **MED, parity.** A `globalconfig=` or `prefix=` in the user's own `~/.npmrc` is not a choice for the parent, which looks at the command line and the environment, but the parent exports it and a child read it back as one, and refused the helper in a global file below a git checkout. Fixed: what the user's own trusted file sets is not a choice, in the child as in the parent; the same value from a user file that a project chose, or another prefix, still is.
- **LOW, fixed.** `unpublish` set the `publishConfig` route only when its manifest had one, so in several workspaces one route could stay for the next; it is reset per manifest, as `publish` does. Five tests pinned nothing, found by breaking the code: the limit of 1 MiB with one counter for both streams, the cache key without the helper path, `String(helper)` for an array or an object. They are pinned now.
- **Recorded.** The three limits above; an empty `tokenHelper` value means not configured and falls back to a stored token without a word (a variable that is unset fails closed); the warning for an OIDC token names the command line or the environment as its source; the branch for a home that is the filesystem root has no test that can fail it (it cannot be set up).
- **Convergence.** One fail-open path and one false refusal, both fixed; the critic of leaks found nothing. An eighth pass is due and it needs to be clean, twice in a row for the freeze.

#### Pass 8

- **Method.** Two critics. One swept every finding of passes 1 to 7 on the final tree, with a probe for each that fails when its fix is gone, and then tried the combinations of the exemptions that the fixes added, looking for one that is also a way in. The other compared an unchanged npm (`ae98c62`) with the prototype for a user with no helper: 36 layouts with about 32 commands, 27 kinds of credential with 27 commands against a recording registry (method, path, every header and the bytes of each body), and 60 cases of the library (bodies, retries, redirects).
- **Found, HIGH, a repository alone.** The project `.npmrc` says `userconfig=<repo>/u.npmrc`, which makes the user file untrusted. `u.npmrc` says `globalconfig=<repo>/g.npmrc` (or `prefix=`, in relative form too), and `g.npmrc` holds the helper line. The rule for the global file looked at the project's keys and at the command line and the environment, not at the keys of the user file it had just refused, so the global file was trusted and its program ran on a plain `npm view`, on Windows and on Linux. A child npm refused, since it reads the environment; the parent was the hole. Every earlier probe started from the project, the environment or the command line, none from a layer that was itself refused.
- **Fixed.** A user file that was refused names no global file: its `globalconfig` or `prefix` makes the global file untrusted too. A trusted user file keeps its own. Two end-to-end cases (`user-file-names-global` and its environment form) and the unit tests fail on the previous prototype and pass on this one, with a control for the user's own file.
- **Found, HIGH, with a CI.** On Unix the default global prefix is `DESTDIR` joined to the prefix; `PREFIX` counted as a choice and `DESTDIR` did not, so a job that sets `DESTDIR` to the checkout trusted a committed file there. Fixed alike, with `destdir-into-the-checkout` and its control.
- **Found, MED, a regression for users with no helper.** Pass 6 skipped the project `.npmrc` when it is the same file as the user file by real path. npm skips it only when the strings are equal, and `config set`, `delete` and `edit` with `--location=project` write the file named by the layer: through a link, they now wrote a file named `(same as "user" config, ignored)`.
- **Fixed.** The project file is loaded as npm always did, and a flag says it is the user's own file under another spelling, which the helper rules use in three places (the key is dropped without a second warning, the project's keys do not refuse the global file, a route value in it is not the project's when the user file is trusted). The flag needs the user path as known before the project file is read, and a path chosen in the environment inside the checkout is refused as before.
- **Confirmed.** All earlier fixes hold on the final tree (about 35 probes, with the mutation that undoes each failing it), and the end-to-end run passes on Windows and Linux. With no helper, requests, headers, bodies and exit codes are identical to the unchanged npm; the differences are the ones named in this document.
- **Convergence.** Two HIGH and one MED, so the phase has not converged. A ninth pass is due, and the freeze needs two clean ones in a row; the last three passes found a way in each time the critic started from a layer or an input the earlier ones had not.
