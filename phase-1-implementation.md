# Phase 1a implementation

How the `tokenHelper` prototype described in [Phase 1a](phase-1-token-helper.md) is built and how it was checked. [Rule by rule](#rule-by-rule) maps each statement in Phase 1a to the test or source behind it, and [sources.md](sources.md) holds what the RFC says about npm, pnpm and others. The earlier, hardened prototype, which also did what [Phase 1b](phase-1b-credential-hardening.md) now describes for every credential (transport, `http:`, redirects, the HTTP cache index, error responses) and located files by device and inode, is kept on the branches `token-helper-hardened` of npm-registry-fetch and npm/cli and `phase-1-hardened` of this repository; 1b grows from them, and nothing below is claimed about those parts.

A coverage shortfall in a suite that already fails on the base is not caught.
- The workflow's targeted step for the npm/cli files the prototype changes runs with `--no-coverage` and checks no coverage; the runner's own file has 100% in a local run of its test.

What the end-to-end run checks:

- Helpers in user config work. Project, `publishConfig` and child-process routes are refused. A helper beats a stored `_authToken` with one warning; a credential on the command line, in the environment or an OIDC token beats a helper.
- A file chosen on the command line or in the environment is refused inside a repository (a `.git` alone, a worktree's `.git` file, `location=global`, a directory below home, a dotfiles repository) and honoured outside one.
- Plain `http:` to another host, and a project's proxy or CA, are refused with the helper not run. Loopback, and the same proxy settings from the command line or the environment, are not.
- A failing helper is npm's error with npm's own exit status, and a helper that runs npm starts no helper in it.
- `NODE_OPTIONS` from a project reaches no helper, also one npm further down, and does reach it where it is the user's own. Redirects and a foreign tarball treat the credential as a stored token's.

The [CI workflow](.github/workflows/prototype.yml) runs all of it on macOS, Linux and Windows, with Node 22.22.2, 24.15.0 and 26.x, except the comparison of every npm/cli suite with and without the prototype, which runs on Ubuntu and Windows with Node 24; on 26.x the prototype's own code runs with deprecations as errors.

Retired with the split, and kept on `phase-1-hardened`: the 2048-combination config matrix, the trust fuzzer and the spelling fuzzer, the probes for containment by device and inode (letter case, Unicode forms, linked temp directories, FAT32 volumes), and the end-to-end checks for redirect hops, error responses and the cache. Phase 1a's location rule looks for a mark in each directory from the file's real path up and compares no identities, so the spellings those probes tried (case, Unicode forms, `\..\`) have no effect on it: a mark is looked up by path, which every spelling serves. The 1b checks return with 1b.

A test that cannot make a link (a file outside the project that links to one inside it) skips itself, and tap counts a skip as a pass. The workflow therefore fails on Linux and macOS, where links can be made, if tap reports any skip in the config tests.

What the macOS runs showed about the platform: a helper script without a `#!` line fails with ENOEXEC there, while Linux runs it through `/bin/sh`. The probes assert it (macOS, and Linux for the second half). The earlier probes' findings about case, Unicode forms and `/var` links were evidence for identity; what the lexical rule relies on is [recorded in sources.md](sources.md#external-facts) and is on the hardened branch.

## Reproducing the checks

The `token-helper` branches are not published; the prototype is the two patches in [poc/patches](poc/patches), made against fixed upstream commits. These are the steps of the [CI workflow](.github/workflows/prototype.yml) (`NPM_CLI_BASE`, `NPM_REGISTRY_FETCH_BASE` and the `prototype` job), in a POSIX shell, starting in an empty working directory that holds a checkout of this repository as `rfc`. The Windows runs also set `core.longpaths` (npm/cli has fixtures deeper than its path limit) and `core.autocrlf false` (the patches have LF endings). Use Node 22.22.2, 24.15.0 or 26.x, and Python 3.12 with `jsonschema` for the Python step.

```sh
git config --global core.autocrlf false
git config --global core.longpaths true      # Windows only
NPM_CLI_BASE=ae98c62586b6fea44114f72e249e246a2981de70
NPM_REGISTRY_FETCH_BASE=6b4159a2519ce5aab26cc4dd8d4596a0b47781d2

# npm-registry-fetch at its base commit, with the patch applied
git init -q npm-registry-fetch
(cd npm-registry-fetch &&
  git fetch -q --depth 1 https://github.com/npm/npm-registry-fetch.git "$NPM_REGISTRY_FETCH_BASE" &&
  git checkout -q FETCH_HEAD &&
  git -c user.name=ci -c user.email=ci@localhost am -q ../rfc/poc/patches/npm-registry-fetch.patch &&
  npm install --ignore-scripts --no-audit --no-fund &&
  npm test --ignore-scripts && npm run eslint --ignore-scripts)

# npm/cli at its base commit, dependencies installed, then the two commits of
# the patch (it raises the npm-registry-fetch floor to ^20.1.0, which is not
# published, so the install comes first)
git init -q npm-cli
(cd npm-cli &&
  git fetch -q --depth 1 https://github.com/npm/cli.git "$NPM_CLI_BASE" &&
  git checkout -q FETCH_HEAD &&
  node scripts/resetdeps.js &&
  git -c user.name=ci -c user.email=ci@localhost am -q ../rfc/poc/patches/npm-cli.patch &&
  node . test --ignore-scripts --workspace @npmcli/config)

# the checks that need the trees (the end-to-end run overlays the prototype's
# npm-registry-fetch on npm/cli's bundled copy and undoes it before it exits)
node rfc/poc/npm-e2e/run.js npm-cli npm-registry-fetch
node rfc/poc/platform-probes/run.js npm-cli
node rfc/poc/helper-fuzz/names.js npm-cli
(cd rfc && python3 -m tests.fuzz_helper --prototype ../npm-cli --seconds 20 --seed 1)
node rfc/poc/claims/check.js npm-cli npm-registry-fetch
```

The workflow also runs the npm/cli files the prototype changes with `node node_modules/tap/bin/run.js --no-coverage` (the step "Test the npm-cli files the prototype changes"), and its `full-suites` job builds a base tree and a patched tree and compares every suite (`node rfc/poc/full-suites/compare.js base next`; the job allows 150 minutes, and its tree setup is in the workflow). With `NPM_CLI=<npm-cli checkout>` set, `python -m unittest discover` also runs the helper comparison of [`tests/test_helper_differential.py`](tests/test_helper_differential.py).

[`poc/full-suites/compare.js`](poc/full-suites/compare.js) is run by CI and counts a test file as a regression only when it fails all three reruns with the prototype and passes all three without it. A file that fails one or two of the three is listed under "failed once, not every time" and the run still passes: a regression that shows up only intermittently is not caught by the gate, so the list has to be read.

## Rule by rule

Each statement of Phase 1a about the prototype is pinned to a test or a check, written as `kind: text`. [`poc/claims/check.js`](poc/claims/check.js) confirms in CI that each one still exists, so a renamed or deleted test fails instead of leaving a claim without evidence.

What the check proves: it finds the text as a substring of the files of its kind. It does not run the test, and finding the text does not show that the test asserts what the row says: that is for the row's wording and for a reader of the test.

Kinds: `fetch` is a test title in npm-registry-fetch `test/auth.js`; `config` a test title in npm-cli `workspaces/config/test/`; `cli` a test title in npm-cli `test/lib/`; `e2e` a scenario or a check in [`poc/npm-e2e/run.js`](poc/npm-e2e/run.js); `probe` a check (not an `info` line) in [`poc/platform-probes/run.js`](poc/platform-probes/run.js).

## Limits

Each row is one of two things, and the kind is in the first column. A **limit** is outside what the Phase 1a checks claim, for the reason given, and says what would make the claim wider. **Deferred** work is something that can be done and is not, with a task that tracks it. A third kind, a defect, is not listed: it is fixed, and the closed ones are named under the table.

How a credential travels after it is sent (redirects, the HTTP cache index, error responses) is [Phase 1b](phase-1b-credential-hardening.md)'s. For 1a the claim about a helper's credential is the refusals in [Which requests get the credential](#which-requests-get-the-credential), and that after them it does what a stored token's does.

| Kind | Not claimed | Why | Wider if |
|---|---|---|---|
| limit | That a helper's credential is hidden from stderr in every encoding: its exact token, and what follows its scheme, is replaced; base64, JSON-escaped, a credential split over lines or cut short are not | The helper is the user's own program and already holds the credential: a helper that encodes it on purpose cannot be stopped by what npm does to its stderr, and guessing at forms gives false positives (an error that says "Token expired" must stay readable) | A helper family is found that writes its credential in another form by default |
| limit | That a helper's credential is better treated than a stored token's after it is sent: a redirect to another port of the registry's host, the HTTP cache index, an error response that echoes the request, `noproxy`, `local-address` | These are in the library and in make-fetch-happen, and the same for every credential; 1a refuses for a helper only what npm/cli can decide before the program starts (plain `http:`, a route a project chose) | [Phase 1b](phase-1b-credential-hardening.md) is adopted: it changes them for every credential, and for a stored token's route as well |
| deferred | That the end-to-end run shows the credential's route against a real https registry: it has no TLS listener, so redirect and tarball parity is shown over loopback `http:` | A listener with a certificate the run trusts costs a generated key pair per run on every OS | The run gains a TLS listener (task to be filed) |

#### The third round

- **Trust.** The roots of the location rule came from the current directory and `localPrefix`, so a repository root with a `.git` and no `package.json`, a nested package, `location=global` in the project and a current directory in no project were missed, and a user's own XDG or `~/.npmrc.work` file was refused when home or the current directory was a root. Fixed: the rule looks at the file's own directories for a `package.json` or a `.git`, stops unchecked at home, and uses no current directory.
- **Split and adoption.** The documents said a helper adds no exposure and behaves like `_authToken`, though it mints a fresh, broad token and fails before the cache. Fixed: plain `http:` and a project's proxy or CA are refused for a helper, and `publishConfig` route keys too; the Summary states the differences and the open decisions name where the maintainers may differ.
- **Protocol.** A credential given for the run lost to the helper, and OIDC had a mask of its own. Fixed: such a credential wins, and OIDC by the same rule.
- **Evidence.** Absences with no control, stale shas and counts, a skipped link test that passed, and documents the workflow did not watch. Fixed: each absence is set beside a control, the numbers are redone, and a skip fails on Linux and macOS.
- **Path identity.** Aliases that a real path does not merge. Stated as a limit, with what would widen it.

#### Fuzz notes

- The pre-split prototype hid the helper's own token only as it is at first, so a token with a quote, a backslash or a character a URL escapes got through when the helper echoed it as JSON, inside a shell's quotes (`set -x`) or percent-encoded. 1a does not hide those forms: they are what a helper that encodes on purpose does, and the Limits row says so.
- The header the prototype makes and the model makes agreed on 242 000 outputs in a run of 60 s, with nothing leaked (measured once on the pre-split prototype, recorded on 2026-10-18, not re-run by CI, which runs the fuzzer for 20 s with a seed of its own).
- `names.js` on Windows tried helper paths with `&`, `^`, `(`, `)`, `!` and a second command among the names in directories named so: those with no `"`, `%` or `!` ran as themselves and nothing else ran, and the others were refused. CI runs `names.js` on each OS.
