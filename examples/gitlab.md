# GitLab

A hypothetical `npm-credential-provider-gitlab` for the npm package registry of a GitLab instance, here `gitlab.example.com`. Nothing here exists: the provider, its name, its keychain layout and the way it obtains tokens are invented, and its behaviour follows the [Phase 2 protocol](../phase-2-credential-provider.md). What it relies on is GitLab's documented behaviour, cited below, and where the documentation does not say, this page says so. The example shows a registry whose URL names a project, so the credential must follow the project; a login that holds only a refresh token while the registry takes other kinds of token, so the provider turns one into the other; and a CI case where the credential already exists in the job's environment.

## Registry and credentials

**URL shapes.** GitLab serves the npm registry at three levels ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)):

- project: `https://<host>/api/v4/projects/<project_id>/packages/npm/`
- group: `https://<host>/api/v4/groups/<group_id>/-/packages/npm/`
- instance: `https://<host>/api/v4/packages/npm/`

Publishing uses the project endpoint. Installing can use any of the three, and the URL needs its trailing slash, since omitting it can cause a 403. An install from the instance endpoint requires a scoped name whose scope is the lowercase root group of the project that holds the package. This provider matches project URLs only (`/api/v4/projects/`) and answers `url-not-supported` for the others, and for the `http:` form of the host, in `get`, `erase`, `login` and `logout` alike (no transcript shows it, because npm never sends such a request: the conformance harness does, to every provider and every kind).

**Credentials.** The documented ones ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)):

| Kind | Scope or role | Lifetime |
|---|---|---|
| Personal, group or project access token | `api`; for an organization that uses 2FA the page names a personal access token with `api` | set at creation; the page recommends a short expiry for personal access tokens |
| Deploy token | `read_package_registry`, `write_package_registry`, or both | none by default; an optional expiry date, which the [deploy token page](https://docs.gitlab.com/user/project/deploy_tokens/) puts at 00:00 UTC on that date |
| CI/CD job token (`CI_JOB_TOKEN`) | the access of the user who triggered the pipeline | valid only while the job runs ([job token](https://docs.gitlab.com/ci/jobs/ci_job_token/)) |

A deploy token's username defaults to `gitlab+deploy-token-{n}` ([deploy tokens](https://docs.gitlab.com/user/project/deploy_tokens/)). A project deploy token can be created and deleted through the API (`POST /projects/:id/deploy_tokens`, `DELETE /projects/:id/deploy_tokens/:token_id`) by a Maintainer or Owner, with `scopes` and an optional `expires_at` ([deploy tokens API](https://docs.gitlab.com/api/deploy_tokens/)). The secret is in the response that creates the token; the API's examples for retrieving one token and for listing carry none, so the provider keeps what it needs (the id) and never expects to read the secret again. An OAuth access token lives two hours (7200 seconds) by default, and a refresh token replaces both tokens when used ([OAuth provider](https://docs.gitlab.com/integration/oauth_provider/), [OAuth 2.0 API](https://docs.gitlab.com/api/oauth2/)). The same API page lists the device authorization grant (its history section puts general availability at GitLab 17.9, its list of flows says 17.1 and later) and PKCE.

**Open points.** The two OAuth pages disagree about the package registry. The provider page says package registry access is covered by `api` (read and write) and `read_api` (read only). The API page says standard OAuth tokens do not allow authenticating to the package registry ([OAuth provider](https://docs.gitlab.com/integration/oauth_provider/), [OAuth 2.0 API](https://docs.gitlab.com/api/oauth2/)). GitLab documents no way to exchange an OAuth token for a short-lived package registry token. The registry page lists a deploy token among the values for `_authToken`, which npm sends as a bearer token. Unverified here: whether an OAuth token with the `api` scope may call the deploy-token endpoint. This example assumes it may. The provider therefore never sends its OAuth token to the registry. It uses the OAuth token only to mint a deploy token for the project, scoped to `read_package_registry` or `write_package_registry`, and sends that.

## Configuration

```ini
# ~/.npmrc (user config)
credentialProvider[]=npm-credential-provider-gitlab --instance https://gitlab.example.com
```

```ini
# the project's .npmrc: registries only, never a provider or a token
@acme:registry=https://gitlab.example.com/api/v4/projects/42/packages/npm/
@acme-tools:registry=https://gitlab.example.com/api/v4/projects/42/packages/npm/
```

The provider is in the global chain, not under a `//gitlab.example.com/` key, because the request must name the project. npm sends the URL that matched: the key's, or, when no key matches, the registry the request chose ([Registry matching](../phase-2-credential-provider.md#registry-matching)). A key for the host, or for `/api/v4/`, would match first and send `https://gitlab.example.com/` or `https://gitlab.example.com/api/v4/`, and the provider could not tell project 42 from project 43. A key per project works too, one line for each, and also gives the right URL. The global form needs one provider line, and the projects stay in the repositories that use them. The cost is that a global provider is asked about every registry, which the hello below removes. The `--instance` argument is for the provider's own use, for example to find the right keychain entry; with or without a trailing slash it names the same instance, and the hello below is the same.

**The reference provider's settings.** [The reference provider](providers/gitlab/provider.js) reads a JSON file named by a `--config <file>` argument that the line above leaves out; it fails to start without one. The file holds the settings the page shows as arguments, here `instance` (the `--instance` argument overrides it), and `clientId`, the id of the OAuth application it logs in with. The rest of the file is for the run: where its store is, which address answers for the host, the clock, the scripted answers of the person ([providers/README.md](providers/README.md)).

The project `.npmrc` carries no token: a `_authToken` there would be a standing secret, and GitLab's own example keeps tokens out of committed files by reading `${NPM_TOKEN}` ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)).

## Hello

```json
{"v":[1],"capabilities":["login","logout","erase","retry-context"],"registries":["https://gitlab.example.com/api/v4/projects/"]}
```

- `"v":[1]` is the only version this provider speaks.
- `registries` lists one entry, the `/api/v4/projects/` path on the instance. It matches at a segment boundary, so it covers every project URL, and npm never asks the provider about npmjs.com or any other host, nor about a group or instance URL on this host ([Registry matching](../phase-2-credential-provider.md#registry-matching)). The scheme is `https:`, so an `http:` form of the host is not served.
- `login` and `logout` because the provider runs the OAuth flow and keeps the refresh token; `erase` because it deletes the deploy tokens it minted when one is rejected; `retry-context` because it uses `httpStatus` on a retry. Capabilities are advisory ([Version negotiation](../phase-2-credential-provider.md#version-negotiation)).

## Install

[install.jsonl](gitlab/install.jsonl). An interactive `npm install` needs `@acme/widgets` from project 42. The provider reads the refresh token from the keychain, refreshes the OAuth access token (the refresh replaces both tokens, so it stores the new refresh token), creates a deploy token for project 42 with `read_package_registry` and an expiry at the first 00:00 UTC after its own limit below, and answers:

```json
{"Ok":{"kind":"get","auth":{"type":"bearer","token":"example-read-deploy-token"},"cache":"expires","expiresAt":1792198800,"operationIndependent":false,"granularity":"scope"}}
```

`expiresAt` is the provider's own limit, an hour from now. GitLab's expiry is a backstop: documented as 00:00 UTC on a date, so the token outlives the limit by up to a day. The provider deletes the token itself on `erase` and `logout`, and before it mints another for the same context (a second `get` for it); it has no timer and does nothing when the session ends, since npm need not wait for the provider to exit ([Session lifecycle](../phase-2-credential-provider.md#session-lifecycle)). The expiry is what limits a token whose deletion never ran. `operationIndependent` is `false` because the provider holds a separate write token: with `true` the cached read token would be found for the `publish` lookup and sent without the presence prompt. `granularity` is `scope`: every `@acme/*` package is a cache hit. Because the registry URL already contains the project, `registry` would give the same cache key while only `@acme` points at project 42; `scope` keeps one token per scope, so that erasing the token of `@acme` leaves `@acme-tools` alone. The second request in the file, for `@acme-tools/lint-rules`, is a new `get` and a second deploy token.

## Publish

[publish.jsonl](gitlab/publish.jsonl). `npm publish` of `@acme/widgets@2.4.1` sends `operation: "publish"` with `version`. The provider mints a deploy token with `write_package_registry`, after the user-presence prompt its policy requires for write credentials (the request is interactive). The prompt names the operation, the package and the version, and says that the token can write packages to the project. A prompt nobody answers within the provider's own 4 minutes 30 seconds, inside npm's 5 minutes, is `other` and mints nothing ([publish-unanswered.jsonl](gitlab/publish-unanswered.jsonl)):

```json
{"Ok":{"kind":"get","auth":{"type":"bearer","token":"example-write-deploy-token"},"cache":"never","operationIndependent":false,"granularity":"package"}}
```

The deploy token is bound to the project, not to the package or the version: GitLab's deploy token has a scope (`write_package_registry`) and a project, and the API has no way to narrow it further. `granularity` `package` is only npm's cache key, and the prompt says that the token can write packages to the project. The RFC's short-lived credential bound to the package and version is therefore not what this provider can make; the token's limit is GitLab's date (below), widened if GitLab documents a narrower token or a finer expiry. `cache: "never"` keeps the write token out of npm's cache, so the next publish asks again, and the provider's own record of the token lets it delete the token on `logout` or when it is asked for a token for the same context again. It does not delete it at the end of the session, or on a timer; the token's expiry date is the limit. `granularity` is still set, since npm keeps it with the credential for any later `erase`. GitLab refuses a publish of a name already in the root namespace with a 400, even for a new version ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)); that is not a credential problem and no retry follows it. GitLab's registry page describes `npm deprecate`, which it says needs permission to delete packages, and says nothing about `unpublish`, deleting a package being a UI or API action for a Maintainer or Owner. It does not say whether a deploy token may deprecate. This provider holds no credential it knows to serve either, so it answers `deprecate` and `unpublish` with `operation-not-supported`. [deprecate.jsonl](gitlab/deprecate.jsonl) and [unpublish.jsonl](gitlab/unpublish.jsonl) show the answers, one command to a session: a `deprecate` and an `unpublish` request, each answered `operation-not-supported`, which npm reports as unsupported without a retry, and nothing minted. An `erase` that names one of these operations gets the same answer and deletes nothing, so it is never taken for the erase of a read token ([unsupported-erase.jsonl](gitlab/unsupported-erase.jsonl)).

[dist-tag.jsonl](gitlab/dist-tag.jsonl) is `npm dist-tag add`. The page says a job token or a deploy token runs `npm dist-tag` commands in a CI/CD job and is silent about other places, so the provider maps `dist-tag` to the write token: the same presence prompt, a deploy token with `write_package_registry`, `cache: "never"`, and no `version`, since the command names none.

**Staging.** The transcripts have no `stage`, `stage-read` or `stage-reject`: GitLab's npm registry page does not mention staged publishing or an approval step for a version, and a search of GitLab's documentation found none (an absence in the docs, not a statement that none exists). A `publish` there is live at once. Were a request with one of these operations to arrive, the provider would answer `operation-not-supported`, as it does for `deprecate`.

## Rejection

[rejection.jsonl](gitlab/rejection.jsonl) is a 401. The registry refuses the read token, perhaps because someone revoked it in the project settings. npm drops its cache entries, sends an erase with the context of the `get` and its `granularity`, then retries once:

```json
{"v":1,"kind":"erase","registry":"https://gitlab.example.com/api/v4/projects/42/packages/npm/","scope":"@acme","package":"widgets","operation":"read","granularity":"scope"}
{"v":1,"kind":"get","registry":"https://gitlab.example.com/api/v4/projects/42/packages/npm/","scope":"@acme","package":"widgets","operation":"read","command":"install","interactive":true,"retry":true,"httpStatus":401}
```

The erase deletes the deploy token the provider minted for that scope. A deletion GitLab does not accept (a 500) leaves the token recorded and answers the erase `other`; the retry that follows deletes it again before it mints, so a second token is never recorded over the first and lost ([rejection-delete-failed.jsonl](gitlab/rejection-delete-failed.jsonl)). It does not touch the refresh token: that is `logout`'s job, and a 401 may come from a URL a lockfile chose ([`erase`](../phase-2-credential-provider.md#erase-a-credential-was-rejected)). The retry mints a new deploy token. If the refresh token no longer works, the provider answers `other` and names `npm login`; it opens no browser on the strength of the 401 alone. [rejection-revoked.jsonl](gitlab/rejection-revoked.jsonl) is that case: someone has revoked the refresh token, and by the time of the retry the OAuth access token has lapsed too. The erase still succeeds, deleting the deploy token while the access token holds, but the retry cannot refresh, so GitLab's `invalid_grant` becomes `other` with the text `run npm login` (only that OAuth error says the login is dead: a refresh that GitLab answers with a 503 is `other` too, but says to try again and names `npm login` only for a failure that keeps coming, [install-refresh-unavailable.jsonl](gitlab/install-refresh-unavailable.jsonl)), and npm fails the command. Erase left the stored refresh token alone, and the provider mints nothing. The request in the file carries no `authChallenges`, because this page does not know which `WWW-Authenticate` value GitLab sends.

[forbidden.jsonl](gitlab/forbidden.jsonl) is a 403. GitLab's own list of causes for a 403 on install includes an expired token, a missing trailing slash, a disabled registry, and a same-name package in the scope ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)), so a 403 here can mean either permissions or an expired token. npm sends no erase after a 403, and the retry follows no erase. The provider deletes the read token it holds for that context and answers with a fresh one, a different credential from the one refused and of the same scope; it never answers a `read` retry with a token that can write. The RFC asks a provider with no other credential to answer `other` "rather than the credential just refused", and a new deploy token of the same scope is not that credential, but it is not likely to fare differently either: a token this provider minted cannot have passed its date while it was still being handed out, so the causes left (a token deleted in the project settings, a registry that is switched off) are ones the provider cannot see. The retry is kept because it is one call, costs at most one live token per context (the old one is deleted first), and is the only way to tell a token removed behind the provider's back from a refusal that stands; a second 403 is reported. (A 401 retry follows an erase that has already deleted it.)

## Login and logout

[login.jsonl](gitlab/login.jsonl). `npm login --registry https://gitlab.example.com/api/v4/projects/42/packages/npm/` sends `login` with `interactive: true`. The provider starts the device authorization grant, or an authorization code flow with PKCE, prints the URL and code on the controlling terminal, polls, and keeps the refresh token in the OS keychain. It answers `{"Ok":{"kind":"login"}}`. No token is written to a file npm reads. The URL and the code come from GitLab and are shown with any control character or bidirectional override replaced by `?`. A `token` in the request, which `npm login` sends when the person pastes one, is not stored: this provider turns an OAuth login into deploy tokens, and a pasted token is neither, so it answers `other` and says so instead of starting a browser login that ignores what was given ([login-token-refused.jsonl](gitlab/login-token-refused.jsonl)). It stops polling when the device code's life, which the server gives with it, is over, or after 4 minutes 30 seconds if that comes first (npm gives a `login` 5 minutes), and answers `other` ([login-unapproved.jsonl](gitlab/login-unapproved.jsonl)); a person who has not approved it by then has not. When the provider has no controlling terminal to print the code on, nobody can approve it: it answers `other` at once, naming `npm login` to be run from a terminal, instead of polling to the deadline, and stores nothing ([login-no-terminal.jsonl](gitlab/login-no-terminal.jsonl)).

[logout.jsonl](gitlab/logout.jsonl). `npm logout` sends `logout`. The provider removes the keychain entry first, so that nothing GitLab does keeps it, then, with what it held, deletes any deploy tokens (`DELETE /projects/:id/deploy_tokens/:token_id`) and revokes the OAuth tokens, each on a best effort basis and within the time npm gives a `logout`, and answers `{"Ok":{"kind":"logout"}}` even if revocation failed, warning on stderr. The same holds in the other direction: a `get` that is still working when a logout lands (a refresh and a mint take time) writes back only what it changed, and only if the store still holds the same login, so a removed entry stays removed ([install-concurrent-logout.jsonl](gitlab/install-concurrent-logout.jsonl): the logout comes between the refresh and the end of the mint, and nothing is stored afterwards). A deploy token whose deletion fails is not kept anywhere after that: with the login revoked and removed, nothing could authorize deleting it later, so it ends on GitLab's date and the warning says so. With no keychain entry and no deploy token held there is nothing to remove, and it answers `not-found` ([logout-nothing-stored.jsonl](gitlab/logout-nothing-stored.jsonl)).

## CI

In a GitLab job there is no keychain and no browser. The provider is in the job image and configured in its global npmrc; the job's `CI_JOB_TOKEN` is already in its environment.

[ci.jsonl](gitlab/ci.jsonl). `npm ci` sends `interactive: false`. The provider checks that the registry host is the job's `CI_SERVER_HOST` and that the project is the job's own `CI_PROJECT_ID`, and answers with the job token:

```json
{"Ok":{"kind":"get","auth":{"type":"bearer","token":"example-job-token"},"cache":"session","operationIndependent":false,"granularity":"registry"}}
```

The token lasts while the job runs ([job token](https://docs.gitlab.com/ci/jobs/ci_job_token/)), so `session` is enough; `operationIndependent` is `false` here too, as on every read answer of this provider, since outside CI it holds a stronger token for `publish`. [ci-publish.jsonl](gitlab/ci-publish.jsonl) is the same for `npm publish`: the pipeline is what authorizes the publish, so the provider asks for no presence it could not get and releases the job token, with `operationIndependent: false`. That holds when the request says `interactive: false`. `CI_JOB_TOKEN` is the environment's, set by whoever ran npm, and a write request that says a person is there is not a pipeline's: it gets the same presence prompt as any write, naming the operation and the package ([ci-publish-interactive.jsonl](gitlab/ci-publish-interactive.jsonl)). GitLab documents `_authToken=${CI_JOB_TOKEN}` for publishing from a pipeline ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)). A job outside a CI environment has no job token and no refresh token, and the provider answers `not-found`. So does a job asked about another project's registry ([ci-other-project.jsonl](gitlab/ci-other-project.jsonl)): the job token is released only for the job's own host and project (`CI_SERVER_HOST`, `CI_PROJECT_ID`), so a dependency in another project is left to a credential behind the provider rather than sent the pipeline's token. A job token that GitLab refuses is not handed out again: it is the only credential here, so the retry is `other` and says so. After a 401 the `erase` before it has nothing to delete ([ci-rejection.jsonl](gitlab/ci-rejection.jsonl)); a 403 on a publish sends no erase, and the retry is the same `other` ([ci-forbidden.jsonl](gitlab/ci-forbidden.jsonl)). A deploy token the user keeps in a CI variable needs no provider: `_authToken=${VAR}` in the user's npmrc is that credential, and a provider that finds neither a job token nor a login answers `not-found`, so the chain falls through to it, with the warning the RFC gives a global chain that declined a registry. The provider reading the variable itself would only copy it, and would have to guess its name and which scopes it has.

## Where it is easy to go wrong

- **Sending the OAuth access token to the registry.** The OAuth 2.0 API page says OAuth tokens do not authenticate to the package registry, while the provider page lists package registry access under `api` ([OAuth 2.0 API](https://docs.gitlab.com/api/oauth2/), [OAuth provider](https://docs.gitlab.com/integration/oauth_provider/)). A provider that sends it works for some GitLab versions and fails for others, and an `api` token is far broader than a read credential. Send a deploy token.
- **Treating `expires_at` as a clock.** A deploy token's expiry is a date, so the GitLab-side lifetime is counted in days, up to a day past the limit the provider means. For a read token the short life comes from the provider: a small `expiresAt` in the answer, and deletion of the token on `erase`, on `logout` and before the next one for the same context. A write token has neither: it is `cache: "never"`, so there is no `expiresAt`, and nothing in the protocol tells the provider when npm is done with it, so it lives until the provider deletes it (the next `get` for the same context, `erase`, `logout`) or until GitLab's date, up to about a day. That is a limit of this example, not a choice: it ends when GitLab documents a shorter expiry or npm gives a provider a signal that a write credential has been used. A provider that relies on GitLab's expiry alone hands out day-long tokens.
- **Leaking deploy tokens.** A token that is never deleted stays valid until its date, or forever when no expiry was set. Delete on `erase`, on `logout` and before minting a replacement, and never create one without `expires_at`. Deleting when the session ends is not available: npm sends `erase` only after a rejection and need not wait for the provider to exit, so the token's own expiry is what limits it (this reference provider has no timer of its own; one that keeps a process alive could add it).
- **Reading the project from the wrong place.** The project is in the `registry` field. A host-level `credentialProvider` key hides it, as the Configuration section says, and a provider that falls back to a default project mints a token for the wrong one.
- **Matching the wrong URL.** The registry page lists the same kinds of token for all three endpoints, and for the instance one requires a scope equal to the root group; for packages spread over projects it uses a group deploy token on the instance endpoint ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)). This provider mints project deploy tokens, which reach one project, so one that served the group and instance URLs with them would fail on dependencies in other projects (an inference from that advice, not a documented error). Answer `url-not-supported`, or list only the project path in hello.
- **Releasing the job token for any project.** `CI_JOB_TOKEN` reaches only its own project by default, plus the projects whose allowlist names it ([job token](https://docs.gitlab.com/ci/jobs/ci_job_token/)), and the registry page says that installing with it a package whose dependencies are in another project gives 404 ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)). A provider that hands it to a registry for any project on the host fails on dependencies in other projects, and sends the pipeline's token to registries it never meant to serve.
- **Starting a login on a 401.** A 401 does not prove the login is dead. Check the refresh token with a refresh before saying so.
- **Widening on a 403.** A 403 for an expired token or a missing trailing slash is not a request for a write token. Answer a `read` retry with a read token or fail.
- **Forgetting `forward`.** GitLab forwards a request for a package it does not hold to npmjs.com unless an administrator or group Owner disables it, and `npm audit` sends its body, including private package names, to the public registry unless run with `--registry` pointing at GitLab ([npm registry](https://docs.gitlab.com/user/packages/npm_registry/)). This is the registry's behaviour, not the provider's, and the provider cannot change it; its README should say so.

## What this registry asks of the RFC

- **A key above the project hides the project ([Registry matching](../phase-2-credential-provider.md#registry-matching)).** The text says `registry` is the URL that matched, and a key for the registry's host is the form most other examples use. For GitLab that URL is too coarse to choose a credential, and the registry URL the user configured (`@acme:registry`) reaches the provider only through the global chain. The RFC could say this where it describes what a provider that needs a path component must configure: a key at or below the path it needs, or the global chain with hello `registries`. The text is correct as it stands; the effect for providers is easy to miss. **In the RFC:** What is sent says that a hello entry is never what is sent, and that a provider needing a path component gets it from the global chain or from a key at or below that path.
- **The end of a session does not say whether npm waits for the provider ([Session lifecycle](../phase-2-credential-provider.md#session-lifecycle)).** "The client closes stdin to end the session, and the provider exits." A provider that deletes the deploy tokens it minted, or revokes a credential, does so after stdin closes, and a call to GitLab may take longer than npm waits before it exits. The RFC should say whether npm waits for the child, for how long, and whether a provider may rely on cleanup at close. Without that a provider with a revocable credential relies on `erase` and a short expiry. **In the RFC:** npm need not wait and sets no deadline, so a provider does not depend on work after stdin closes.
- **A 403 carries no erase and does not say which credential it refused ([`erase`](../phase-2-credential-provider.md#erase-a-credential-was-rejected)).** GitLab's documentation lists an expired token among the causes of a 403 on install. By the table the credential is not erased and the retry carries `httpStatus: 403` and the challenges if the registry sent any, without the `granularity` or the credential that was refused. The retry still names `registry`, `scope`, `package` and `operation`, so a provider that keeps its own record of what it handed out for that context copes; the RFC does not say that it should. It would help to say so, and either state that a provider keeps its own record of what it handed out, or let the retry carry what an erase carries. **In the RFC:** the RFC says the retry names the context, not the credential or the reason, and that a provider which needs the credential keeps its own record.
- **No place for a credential that must be created and deleted** ([`erase`](../phase-2-credential-provider.md#erase-a-credential-was-rejected), [Caching](../phase-2-credential-provider.md#5-caching)). With `cache: "never"` npm sends an erase only on a rejection, so nothing tells the provider that a write token it minted has been used and may be deleted. The provider must delete when it is next asked for one, on `logout`, or let the expiry end it. This is a consequence of the design, not an error in it; a short note would save provider authors from looking for a signal that does not exist. **In the RFC** by the same Session lifecycle sentence: cleanup after stdin closes is not guaranteed, so the token's expiry limits it.
