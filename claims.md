# Evidence for the RFC's claims

Every checkable statement in [Phase 1](phase-1-token-helper.md) and [Phase 2](phase-2-credential-provider.md), and what backs it.

- **External facts** were checked against the source on the date given in the row. The copies in `.refs/` were fetched on 2026-10-20, after some of those dates: a copy is the page as it stood on the 20th.
- **Statements about the prototype** are pinned to a test or a check, written as `kind: text`. [`poc/claims/check.js`](poc/claims/check.js) confirms in CI that each one still exists, so a renamed or deleted test fails instead of leaving a claim without evidence.
- **What the check proves:** it finds the text as a substring of the files of its kind. A `spec` row is a key of the policy; a `py` row names a test module, and only the `module.test_name` or `module.Class.test_name` form is looked up inside it. It does not run the test, and finding the text does not show that the test asserts what the row says: that is for the row's wording and for a reader of the test.

Kinds: `fetch` is a test title in npm-registry-fetch `test/token-helper.js`; `config` a test title in npm-cli `workspaces/config/test/`; `cli` a test title in npm-cli `test/lib/`; `e2e` a check in [`poc/npm-e2e/run.js`](poc/npm-e2e/run.js); `probe` a check (not an `info` line) in [`poc/platform-probes/run.js`](poc/platform-probes/run.js); `spec` a key in [`spec/policy-v1.json`](spec/policy-v1.json); `py` a test module in [`tests/`](tests), which proves only that the file exists unless the row names the test as `module.test_name` or `module.Class.test_name`; `js` a test title in [`examples/providers/*.test.js`](examples/providers); `rs` a Rust test function under [`poc/rust/crates`](poc/rust/crates).

The readers were right, and the schema's pattern was tightened after it.
- Before that run, a run of 100 s covered 756 000 messages with none in dispute (measured once, not re-run by CI).

## What these documents do not claim

Not a list of things left to do: each is outside the claim, for a reason, and each says what would make the claim wider. What is merely not yet checked is under "Not verified".

| Not claimed | Why | Wider if |
|---|---|---|
| That a helper's credential is hidden from stderr in every encoding: the helper's own token is hidden as it is, as JSON, inside a shell's single or double quotes and percent-encoded (both cases of the digits), and credential-like text is masked; base64, hex, a credential split over lines or cut short are not | The helper is the user's own program and already holds the credential: a helper that encodes it on purpose cannot be stopped by what npm does to its stderr, and every other encoding is unbounded in number. The forms hidden are the ones an accident produces: a token echoed by `set -x`, quoted in an error body, in a logged URL | A helper family is found that writes its credential in another form by default, as `set -x` does in a shell's quotes |
| That the credential never reaches the HTTP cache index on disk | It takes a change to make-fetch-happen, which is not this prototype's to make; the cost and the way to avoid it are in Phase 1 | make-fetch-happen leaves `Authorization` out of the index whatever a response's `Vary` says |
| That the scheme rule and the transport rule are shown against a real https registry end to end: the end-to-end run has no TLS listener, so it shows the http: half (a registry on a network address gets no credential, a repository's proxy sees none) and the unit tests show the rest, with a mocked make-fetch-happen for the options it is given, not for what it does with them | A TLS listener with a certificate the run trusts costs a generated key pair per run on every OS, which the unit tests already cover for the decision itself; what is unshown is only that make-fetch-happen honours `proxy`, `ca` and `strictSSL` per request, which its own tests and the proxy control (`e2e: control: a stored token goes through`) show for `proxy` | The run gains a TLS listener |

## Not verified

- Phase 2 client behaviour that only an npm implementation can show, as npm has no Phase 2 client (the Rust `mock-client` is a test harness for the protocol, not an npm client): masking and control-character stripping of provider stderr and error messages, the `.cmd` argument quoting and refusals, the Windows working-directory limit for providers, `${VAR}` expansion of per-registry provider lists, who owns the provider process, and that an interactive request goes through npm's input bracket.

- make-fetch-happen as shipped in npm 12 recording a header named in `Vary` in the cache index: seen in a historical version's source and in an audit probe, not re-read in the current source.
- Node's Windows installer shipping a builtin `npmrc` that sets `prefix=${APPDATA}\npm`: recalled, not checked on an installed copy.
- registry.npmjs.org answering an anonymous request for a private package with 404 rather than 401: npm's own 404 message allows for it and it is commonly reported, but no request was made for this document.
- Which registries send `Vary: Authorization`: none of the mainstream ones were found to, but no header survey was made.
- Whether a helper path with whitespace in it is refused or accepted the same way on Windows by the prototype and by the model: compared on Linux and macOS in CI and in a Linux distribution on Windows, on Windows only for paths with no whitespace, because Win32, Python and libuv each normalize a trailing space or dot, a slash after a file and a verbatim path differently.
- Windows filesystems without inode numbers (FAT, some network shares): the fallback to spellings is tested with a simulated zero inode, not on such a filesystem.
